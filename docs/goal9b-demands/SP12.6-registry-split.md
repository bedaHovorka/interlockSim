# SP12.6 — PathReservationRegistry split: demands on Goal 9B

**Issue:** bedaHovorka/interlockSim#1172 (Goal 1B, SP12 leaf 6, parent #1159) · **Date:** 2026-10-11

SP12.6 split `PathReservationRegistry.kt` (1,758 lines, over detekt's 800-line `LargeClass`
limit) along its three ownership concerns. It is a pure extraction: the registry keeps its whole
public interface and every behaviour, including the stale-ownership behaviour that #1173 and
#1174 will change. This note records which registry seams a Goal 9B dispatcher may call and
which must stay private, so Goal 9B work does not grow a second door into the ownership state.

## The units

| Unit | Visibility | Lines | Owns |
| --- | --- | --- | --- |
| `PathReservationRegistry` | public | 750 | the public facade; composes the operations that span units |
| `BlockOwnershipTable` | internal | 244 | train <-> block maps, registration timestamps (#975) |
| `SwitchOwnershipTable` | internal | 220 | switch claims, flank purpose, stale-claim rule (#1065/#1076/#1103) |
| `PathInfoStore` | internal | 519 | stored PathInfo per train, trim bookkeeping (#1050/#1063/#1067) |
| `PathInfoMerger` | internal | 376 | stateless merge algorithm and its four fail-safe aborts (#834/#904/#944) |

The two cross-unit operations stay in the registry, so there is still exactly one place for each:
whole-route teardown (`unregister`: blocks, PathInfo, every switch claim) and the per-block
release funnel (`unregisterBlock`: the block, then a reclaim of every switch claim at its ends
that is stale afterwards). Both the switch table and the PathInfo store read held blocks through
the same read-only function reference (`BlockOwnershipTable.getBlocks`, a copy); neither unit can
mutate another's state.

All units log through the registry's logger (`registryLogger`), so log configuration and
log-capturing tests (`MergeAbortSimSurvivalTest`) see the category they saw before.

## Seams a Goal 9B dispatcher may call

A dispatcher observes and requests; it never mutates ownership directly. Read-only queries are
safe to call from a dispatcher (they change no state and cannot leave a half-applied
transaction):

- Block ownership: `getOwner`, `getBlocks`, `isRegistered`, `isBlockAvailable`,
  `getOccupant` / `getOccupantName` / `isOccupied` / `getOccupiedBlocks`, `trainCount`,
  `blockCount`, `getRegisteredAtSimTime` (a fact, not an expiry policy — #975/#1174 decide that).
- Switch ownership: `getSwitches`, `getSwitchOwner`, `isFlankProtected`, `isOwnedByOtherTrain`,
  `isStaleSwitchOwnership` (diagnostic only — releasing is not the dispatcher's call).
- PathInfo: `getPathInfo`, `isPathExtendedBeyond` (the rule-based arm's "route already set"
  check in `ShuntingLoop`), `nonContinuingCandidateReason`, `pathInfoEndAfter`,
  `isValidPathInfoEnd`, `canTrimPathInfoTo`.
- Events: `addBlockOccupancyListener` / `removeBlockOccupancyListener` (synchronous, on the
  simulation thread — a listener must not call back into a mutating seam), `emit`
  (producer-side dispatch of an event to the listeners; a dispatcher registers a listener
  instead of calling it).
- `createBlockAvailableCondition`: for a kDisco process that waits on a block, never for polling.

The dispatcher-side release components that exist today — `OrphanReservationSweeper` and
`RegistryPartialRouteReleaser` in `:dispatcher-agent` — also call the release seams below. They
are part of the interlocking side of the seam, not of a dispatcher's decision logic, and they
keep working unchanged against the registry interface.

## Seams that must stay private to the interlocking

Every mutating registry operation is part of a reservation transaction owned by
`DefaultPathReservationService` or `DefaultInterlockingFacade`. Called alone from a dispatcher,
each one can leave blocks, switches, signals and PathInfo disagreeing:

- `registerAtomic`, `registerSwitches`, `registerFlankSwitches`, `registerPathInfo` — a
  reservation without its signal clearing and rollback; Goal 9B requests a route through the
  facade (`InterlockingFacade`) or `PathReservationService`, never through the registry.
- `unregister`, `unregisterBlock`, `unregisterSwitch`, `unregisterSwitches`,
  `reclaimStaleSwitchOwnership` — releases without the signal-to-STOP and approach-lock rules of
  the service (#1050); the sweeper/releaser path above is the only sanctioned non-service caller.
- `restorePathInfo`, `trimPathInfoTo`, `trimPathInfoToHeldBlocks` — PathInfo surgery that is only
  valid right after the matching block release or rollback.
- `clear` — simulation reset only.
- Everything in `BlockOwnershipTable`, `SwitchOwnershipTable`, `PathInfoStore`, `PathInfoMerger`
  and `getSwitchClaim`: `internal` to `:core`; a dispatcher module cannot see them, and Goal 9B
  should not ask for them to be widened — what it needs is a query on the registry facade.

**Goal 9B demand:** if a dispatcher needs a fact the read-only list does not give (for example
*why* a switch is held — flank or running — or *when* a holding became stale), the demand is a
new read-only query on `PathReservationRegistry`, not access to a unit.

## Acceptance evidence

### API diff — no public signature changed

`javap -public` of every `PathReservationRegistry*.class` (`:core` JVM target) before (base
9953beb4) and after the split:

- `PathReservationRegistry` and all nested public types (`RegistrationResult`, `Conflict`,
  `Success`, `ConflictReason`, `MergeOutcome`, `Merged`, `Aborted`, `PathInfoEnd`): **identical**.
- The constructor is unchanged (`(SimulationContext, Function0<Double>)` plus the default-argument
  synthetic); `context` and `simTimeSource` became plain constructor parameters instead of private
  properties, which is not visible API.
- File facade `PathReservationRegistryKt`: three synthetic `access$` helpers moved to
  `PathInfoStoreKt` with the private helpers they served; it gained `getRegistryLogger()`, the JVM
  getter of the `internal` shared logger (not part of the Kotlin API).
- Two new package-private synthetic classes for the function references the registry passes to
  its units.
