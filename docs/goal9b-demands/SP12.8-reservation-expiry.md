# SP12.8 — Reservation expiry follows progress: seams for Goal 9B

> SP12 status index: [SP12-routing-decomposition.md](SP12-routing-decomposition.md) collects the Goal 9B seam list, the duplicate-check report and the size numbers for all SP12 leaves (SP12 is still open, #1159). This page keeps the leaf evidence.

**Issue:** bedaHovorka/interlockSim#1174 (Goal 1B, SP12 leaf of #1159; absorbs and closes #975) ·
**Date:** 2026-10-25 · `[sim]` behaviour change

Before SP12.8, nothing in `:core` released a route its train never entered. A granted route was
released only by being consumed (the train's `Tail` leaving a block, journey completion) or by an
explicit `releasePath`, so "a reservation does not outlive its train" held only for runs that
wired the dispatcher's `OrphanReservationSweeper`. `:fast-sim`, `multiTrainLoop` and every
`SynchronousDispatcherWiring` run had no such guarantee.

SP12.8 moves the guarantee into the reservation kernel (phase 1 of the traffic-simulation-expert's
ruling):

- **Progress = the train's newest block registration.** No new state: the registry already stamps
  every block with the simulation time it was registered (`blockRegisteredAt`, the #975 stepping
  stone). A new claim (a route extension) restarts the clock; re-registering a block the train
  already holds does not.
- **Pure query:** `PathReservationRegistry.expiredHoldings(ttl, now)` names every train whose held
  blocks are all RESERVED with nobody on them (`isTrainOnBlock`, the route release's own predicate,
  read live) and whose newest registration is at least the TTL old.
- **Only trains that occupy nothing expire whole.** A train standing on any block is exempt from
  this rule at any age: entering a reserved block is not a registry write, so registration age says
  nothing about a train on the track. The registry's query judges only the blocks it attributes to
  the train, so the service also drops every candidate that physically stands on any other block
  (`RouteCandidateScreen.standingTrainIds`, the graph scan behind `footprintOf`, read once per call
  since #1229 — the Issue #893 state of a train on a block with no registry entry). The stalled
  RESERVED tail of a train on the track is **phase 2, #1220** — see
  [Phase 2](#phase-2-the-stalled-tail-of-a-train-on-the-track-1220) below.
- **Release only through `releasePathDetailed`** — the release `cancel_route` and the sweeper use:
  signals to STOP first, blocks cancelled, switches unlocked and unregistered, PathInfo removed,
  one `BlockReleased` per block, and the Issue #1050 approach lock honoured. Never `releasePath` or
  a raw `unregisterBlock`.
- **TTL:** 60.0 simulated seconds, `DefaultPathReservationService.DEFAULT_RESERVATION_TTL_SIM_SECONDS`
  (a constructor parameter; the same value as the sweeper's `DEFAULT_STALE_AFTER_SIM_SECONDS` and
  the #943 WARN horizon). Simulation time only: `NavigationWallClockTripwireTest` fails on any
  wall-clock read under `context/navigation/`.
- **Triggers, both:** the expiry runs at the top of `reservePath` and `reservePathToAny` (once per
  request, exempting the requesting train; `reservePathToAnyNextSemaphore`'s attempts call the
  internal overload and `isPathToAnyNextSemaphoreAvailable` stays pure), and once per control step
  in `ShuntingLoop.iteration()` (after the terminated-train prune, before the observation snapshot
  and the control step) and `MultiTrainLoop.iteration()` (next to `releaseFreeResources()`).
- **Observable:** every completed expiry logs `Reservation expired for '<train>': ...` at INFO with
  the age (one decimal) and the TTL, and the number of blocks that call released (after an
  approach-lock deferral, only the remaining head); a deferral logs
  `Reservation expiry deferred for '<train>': ...`. A release that throws is contained and logged
  at WARN once per train. The service counts completed expiries (`expiredHoldingCount`, internal).
  Since #1243 every completed expiry of either phase is also announced as a `ReservationExpired`
  kDisco custom event (train, `kind` = `WHOLE_HOLDING` or `OCCUPYING_TRAIN_TAIL`, the blocks the
  completing call freed, the blocks the train stands on, the unrounded age, the TTL, the sim time);
  subscribe with `SimulationEnvironment.onReservationExpired` before `run()`. A deferral, a refused
  release and a release that threw announce nothing. Each `onReservationExpired` subscriber is
  isolated: one that throws is logged at WARN (`A ReservationExpired listener failed ...`) and the
  subscribers after it still get the event. A raw `onSimulationEvent` subscriber is not isolated:
  kDisco's bus has no guard, so one that throws ends delivery to the subscribers after it, and the
  expiry only contains the failure (WARN `... could not be delivered`) so the completed expiry stands.
  The expiry is counted before it is delivered.

## Seams a Goal 9B dispatcher may call

| Seam | Caller today | Why it is safe for a dispatcher |
| --- | --- | --- |
| `ReservationExpiry.expireStaleReservations()` via `RoutingServices.getReservationExpiry()` | `ShuntingLoop.iteration()`; `MultiTrainLoop` through its `PathReservationService` (whose superinterface it is) | Idempotent and rule-bound: it releases only what the kernel rule already condemns, through the same approach-locked release. Calling it more often changes nothing but the moment of release. A dispatcher does not need to call it — the loops and every `reservePath` already do. |
| `reservePath` / `reservePathToAny` | unchanged callers | Now expire stale holdings of other trains first, so a contender's single call can succeed where it used to report `AllPathsBlocked` until a sweeper intervened. |
| `releasePathDetailed` (via `NetworkActuatorPort.releaseRoute`) | `cancel_route`, `OrphanReservationSweeper` | Unchanged (SP12.2). The kernel expiry uses the same call, so a dispatcher cancel and a kernel expiry of the same holding simply share the work. |

## Seams that must stay private to the simulation

| Seam | Owner | Why a dispatcher must not call it |
| --- | --- | --- |
| `PathReservationRegistry.expiredHoldings` | `DefaultReservationExpiry` (the service's internal collaborator) | A query over registry internals; its answer is only meaningful together with the release policy that acts on it. |
| `isTrainOnBlock` | `RouteReleaser` / `BlockOwnershipTable` (`internal`) | The one "a train stands here" notion of release and expiry; a second caller with its own reading would let them disagree. |
| the TTL | constructor of `DefaultPathReservationService` | A behavioural constant, not a runtime knob: changing it changes when live routes are withdrawn. Decide it in simulated seconds and in control steps (60 s = 30 steps of 2.0 s). |

## Failure modes and how phase 1 handles them

| Failure mode | Phase 1 handling |
| --- | --- |
| **Slow train** | A train that has entered any block occupies it and never expires, however slowly it moves. A train that has not entered its route 60 simulated seconds after its newest claim does expire — that is a granted route nobody uses (including a queued train the AI dispatcher never approved, which the sweeper already treated the same way). On `vyhybna.xml` every granted route is entered within seconds: the clean-baseline tripwires (rule-based `ShuntingLoop` 600 s, three-train `MultiTrainLoop`) expire nothing. |
| **Approach lock** | The release is `releasePathDetailed`: a RESERVED block whose entry signal shows a proceed aspect is kept (a train may be committed to it), the signals drop to STOP, the rest is freed. The holding stays in the query and is freed on a later call once the 1.0 s booking window has closed in simulation time — or, if the committed train booked the block meanwhile, it now occupies track and is exempt for good. Pinned by `ReservationExpiryTest` ("deferred, not forced"). |
| **Same-instant entry race** | The expiry reads occupancy live (`isTrainOnBlock`: an occupant or an OCCUPIED booking) at the moment it runs, on the single simulation thread. A train that booked its first block earlier in the same instant occupies track and is exempt; one that has only read the proceed aspect is protected by the approach lock, whose window is kept through its expiry instant itself (`>=`), so a release scheduled first at that same instant still defers. |
| **Re-registration** | A block keeps its first timestamp while its owner re-registers it, so asking for the same route again is not progress; only a new block restarts the clock. The requesting train is exempt from the expiry at the top of its own `reservePath` / `reservePathToAny` (traffic-simulation-expert ruling): its new claim restarts the clock, as it restarts the #847 sweeper's. Expiring it first would empty its footprint, so `rejectNonContiguousStart` would pass vacuously (ruling D8) and a mid-station extension would be granted as an orphan route. If the request fails, the next loop tick expires the holding. Pinned by `ReservationExpiryTest` (an extension at t=60 of a segment granted at t=0 succeeds and keeps the segment until the loop tick at t=120). |
| **Metric double count** | A holding the approach lock defers is counted, and logged as `Reservation expired`, once — on the call that frees its last block; the deferring call logs `Reservation expiry deferred` and counts nothing. `BlockReleased` goes out exactly once per block (tail on the first call, head on the completing one), pinned by `stalledReservationExpiresAfterTtl`. The sweeper counts only releases its own calls performed. |
| **Sweeper/kernel race** | Both run on the simulation thread, never concurrently. The kernel's clock starts at the registration and its loop tick runs before the control step that runs `sweep()`, so it acts no later than the sweeper. A holding the kernel has half-released shows the sweeper a changed held set, which restarts the sweeper's own clock; the kernel completes it. Both use the same idempotent `releasePathDetailed`, so whichever runs second finds less or nothing. |

**Effect on the sweeper's metrics:** in AI runs the kernel now releases the un-travelled
whole-route case first, so `OrphanReservationSweeper.staleReleaseCount` falls toward zero. Its
phantom-owner releases (on sight, before any TTL) are unaffected, and so, in general, is the
occupying-train tail (`partialReleaseCount`): phase 2 (#1220) acts no earlier than the sweeper on
it (see [Phase 2](#phase-2-the-stalled-tail-of-a-train-on-the-track-1220)). A falling
`staleReleaseCount` is the expected outcome, not a regression.

**Known gap, still open:** if an approach-lock partial release leaves a block FREE but still
registered (its drop failed and was contained in `RouteReleaser.releaseAllBut`), the train no
longer holds only RESERVED blocks, so the kernel stops judging it and its deferred head is never
freed in a run without the sweeper. With the sweeper wired, the sweeper's whole-route rule still
reclaims it. Phase 2 (#1220) does not close it: its ruling covers a train that *stands* on part of
its holding, and such a FREE registered block is in neither of the query's lists.

## Goal 9B demands recorded here

- **A dispatcher learns of an expiry only indirectly** (one `BlockReleased` per block, the INFO
  line). A `ReservationExpired` event naming the train, the age and the TTL would let a dispatcher
  tell "my grant was withdrawn" from "the train consumed its route". **Addressed by #1243 (kind
  names the tail case):** `ReservationExpired` names the train, the phase (`WHOLE_HOLDING` /
  `OCCUPYING_TRAIN_TAIL`), the freed and the kept blocks, the age and the TTL. Its reference
  consumer, the test-source `ExpiredRouteQuarantine` in `:dispatcher-agent`, stops re-granting a
  train whose reservation expired twice while it stood on the same blocks
  (`ExpiredRouteRegrantCycleTest`); wiring a consumer in production is a Goal 9B follow-up.
- **One TTL for every train.** Per-train or per-route-class horizons (a long entry approach on a
  larger station) are a Goal 9B question; phase 1 keeps the single 60 s constant.
- **Phase 2 (#1220):** done — see below. The tail case is announced as a `ReservationExpired`
  event of kind `OCCUPYING_TRAIN_TAIL` since #1243.

## Phase 2: the stalled tail of a train on the track (#1220)

Phase 1 leaves a train that stands on part of its route alone, at any age. Phase 2 frees the
RESERVED tail of such a train once it has truly stopped advancing — never that of a moving one,
which would throw signals to STOP in front of it. The traffic-simulation-expert's ruling D1–D9
(posted on #1220 before any code) sets every rule below.

- **Signal: a kernel-side progress snapshot, no `sim/` change (D1).** Per occupying train
  `TailStallTracker` (the stall judgement `DefaultReservationExpiry` delegates to) keeps *(occupied block set, RESERVED block set,
  `occupant.distanceToSemaphore()` reading)*, read through `TrackOccupant`. The reading is a change
  detector, not a distance: it moves while the train moves inside a block, jumps at block
  boundaries and on a new leg, and is constant while the train stands.
- **Stall rule (D2).** The stall clock restarts whenever any component changes, the reading by more
  than 0.01 m (`TailStallTracker.PROGRESS_THRESHOLD_METERS`) from the reading the clock
  started at — an asymptotic approach (Issue #797) creeps by less, so a train that advances under
  1 cm in the TTL is stalled, while 4 mm per tick adds up to progress within three ticks. A new
  block registration changes the RESERVED set, so a route extension restarts the clock too. A train
  with no readable occupant of its own (an OCCUPIED booking, or somebody else on its block) is not
  judged on that call, and its clock is dropped: the first readable call after the gap starts a
  fresh one, so the tail is never freed without a full TTL of readable standstill. The clock starts at the first call that sees the train; the loop ticks every
  2 s, so that is within one control step of the train entering.
- **State in the expiry, a pure query in the registry (D3).** The snapshots and their
  `sinceSimTime` live in the expiry's own `TailStallTracker` and are dropped when a train leaves the set
  (it left the registry, or stands on nothing it holds). The registry adds only
  `PathReservationRegistry.occupyingHoldings()` (internal): every train standing on a block it
  holds, with those blocks and its un-entered RESERVED tail (`isUnenteredReservation`, next to
  `isTrainOnBlock` in `TrainOnBlock.kt`).
- **Release unchanged (D4).** A train stalled for the TTL hands its tail to
  `RouteReleaser.releasePathDetailed`: occupied, approach-locked and deferral-window blocks are
  kept, the rest is freed, `unregisterBlock` reclaims stale switch claims, and the PathInfo is
  trimmed to the held blocks. Nothing is freed when the PathInfo cannot be trimmed to the kept
  blocks. The expiry's own release is not progress: the snapshot is taken again afterwards with the
  same clock, so a deferred head is retried on the next call. If the PathInfo trim makes the train
  rebuild its leg, though, `distanceToSemaphore()` jumps, so the stall clock restarts and an
  approach-locked head kept by the first call waits one more TTL (accepted under D2: the reading is
  a change detector and a rebuilt leg is a change).
- **Logging (D5, #1228 item 4).** A completed tail expiry logs `Reservation tail expired for
  '<train>': ...` at INFO, counts once (`expiredTailCount`, internal) and is announced once as a
  `ReservationExpired` event of kind `OCCUPYING_TRAIN_TAIL` (#1243). A deferral logs `Reservation
  tail expiry deferred for '<train>': ...` at INFO once per train and at DEBUG afterwards — phase
  1's `Reservation expiry deferred` line follows the same once-then-DEBUG rule now. A stalled train
  whose tail is empty is skipped silently: no release call, no line.
- **#943 waiter and the PR #940 waiter (D6).** A train standing at a STOP signal waiting for a route
  has consumed its leg and holds only occupied blocks, so phase 2 has nothing to free; no
  aspect-based exemption exists. The PR #940 waiter — a RESERVED tail that does not reach a
  forward-facing separator — loses that tail after the TTL. The kernel no longer grants such a
  route (the #1188 / #1200 end guards), so its pin builds the state by hand.
- **Approach lock, booked-not-entered trains, TTL (D7, D8).** No new rule; one TTL, 60 s,
  `DEFAULT_RESERVATION_TTL_SIM_SECONDS`, for both phases, the sweeper and the #943 horizon.
- **Exemptions shared with phase 1.** The requesting train is exempt at the top of its own
  `reservePath` / `reservePathToAny` (its snapshot is neither judged nor taken); a throwing release
  is contained and logged at WARN once per train.
- **Not judged by phase 2:** a train standing on a block the registry does not attribute to it (the
  #893 state) — the query reads only registry-attributed blocks, so its separate un-entered route is
  kept by both phases, as before.

**What it means in a run.** The `ReservationTailExpiryScenarioTest` run puts `zA` back to STOP in front of an eastbound train in
`kA`; the train stands, its tail is freed once after the TTL, the dispatcher sets a new route from
`zA`, other trains are granted the freed blocks, and the run raises no conflict, collision warning or
`errorStop`. Without phase 2 that tail is never freed in a run without the sweeper.

**Where phase 2 defers forever (by D4, not a defect).** In `vyhybna.xml` the block after a home
signal ends at a switch, so a tail can be cut only right after a block the train stands on whose
far end is a signal facing it (`kA` → `zA`, `kB` → `zB`, `k1`/`k2` → their exit signals). Two
standing shapes therefore keep their tail:

- the train stands on a block that ends at a switch or a rear-facing signal — the PathInfo cannot
  end there;
- the train stands at a signal its dispatcher re-clears every tick (the #1060 "awaiting
  extension" shape: navigation answers `OwnershipConflict` although the route runs on, so the
  rule-based dispatcher re-requests the train's own route). Approach locking then keeps the block
  behind the proceed aspect each call, and the cut after it falls on a switch.

In both, `releasePathDetailed` frees nothing on every call. Since #1242 the releaser treats the two
apart, and each of its two `... cannot be trimmed ...` lines is INFO once per train, then DEBUG
(before, one WARN on every call). Once per train is not once per stall episode: the releaser logs
the line at INFO again only after a release of that train went ahead or the train left the
registry. The expiry's own `Reservation tail expiry deferred` line is INFO once per stall episode.

- In the first shape no signal reset can ever let a later call cut, so the releaser refuses before
  any signal or block change, as `RegistryPartialRouteReleaser` does: the train's aspects stay as
  granted and nothing else changes (`releasePath: refused for '<train>' -- ...`).
- In the second shape only the approach-locked block stops the cut; the cut after the occupied head
  is valid. There the signal reset is the step that lets a call past the booking window free the
  tail (a stopped train no dispatcher re-clears loses its tail that way), so the releaser still
  resets the signals (`releasePath: approach lock for '<train>' -- ...`). In the #1060 shape the
  dispatcher re-clears every tick, so the aspect still flips STOP/proceed every 2 s: that flap is a
  symptom of #1060's stall, not of the releaser.

**Sweeper.** `OrphanReservationSweeper` keeps its own held-set rule for the occupying-train tail:
its clock restarts only when the RESERVED tail changes. The kernel's stall clock restarts on that
and also on a change of the occupied set or of the reading, so it never starts earlier: phase 2
acts **no earlier** than the sweeper. It acts on the same tick only when the train has stood still,
on the same blocks, since its tail last changed -- and then first, because the kernel tick runs
before the control step that sweeps. A real train brakes to a stand after its last block entry
(in the scenario run it rolled on for about 16 s after the put-back), so with the sweeper wired the
sweeper usually reclaims a stopped train's tail first and `partialReleaseCount` does not fall in
general. Phase 2 is the guarantee for runs without the sweeper (`:fast-sim`, `multiTrainLoop`, the
rule-based loops). The sweeper alone also reclaims the tail of a train whose held set is unchanged
but which is still moving (it has no progress reading); a tail that cannot be trimmed after the
occupied head is kept by both.
