## Which seams a Goal 9B dispatcher may call

A dispatcher reaches signals only through the `PathReservationService` interface (and, above
it, the interlocking facade). Those entry points stayed on the service:

| Seam | Dispatcher use | Why |
| --- | --- | --- |
| `PathReservationService.reservePath` / `reservePathToAnyNextSemaphore` / `reservePathToAny` | **call** | Signals are cleared as the last step of an atomic grant: blocks, then switches, then the START signal, then intermediate semaphores. A dispatcher asks for a route; it never asks for an aspect. |
| `PathReservationService.releasePath` / `releasePathDetailed` / `unregister` | **call** | Release resets every aspect the train still owns (last-writer-wins). |
| `PathReservationService.hasClearedSignals(trainId)` | **read** | A cheap "is any proceed aspect still lit for this train" check; exact, because the ledger never holds an empty entry. |
| `PathReservationService.recordExternalClearedSemaphore` | **call only when the dispatcher itself writes an aspect outside a reservation** (as `DefaultInterlockingFacade` and `DefaultNetworkActuatorPort` do) | Keeps a single signal ledger (#893 task A6); without it a manual aspect outlives every release. |
| `PathReservationService.resetSemaphoresForReleasedBlocks` | **call only inside its documented scope** (suffix/rearmost releases on a non-revisiting route) | It does no route-position validation of its own. |

## Which seams stay private

Both new classes are `internal`; nothing outside the reservation kernel should hold them.

- **`RouteSignalConfigurator.configure*`** — calling one outside a reservation would light a
  signal over track that is not reserved, or over a switch that is not yet set: the order
  *switches before signals* (#300/#291/#742) is a safety property of `reservePath`, not of the
  configurator. The G4 rear-facing rejection (`StartSignalResult.RejectedG4`) already reaches a
  dispatcher as `ReservationResult.GeometricallyImpossible`.
- **`ClearedSignalLedger` reset helpers** — each encodes one rollback situation (failed START
  write, aborted merge, bypass rollback) and depends on a snapshot taken by the caller before
  the attempt. Out of that context they either miss an aspect or drop one another train needs.
- **`facesDirectionOfTravel` / `startFacesTravelDirection`** — geometric helpers of the
  configurator; a dispatcher that needs facing information should get it from perception
  (`DefaultNetworkPerceptionPort`), not from the kernel.
- **`allSemaphores()`** (the #965 semaphore cache) — not signal configuration: its only production
  reader is `reservePathToAny` step 1. It stays `internal` on the service in SP12.3 and moves to
  `ReservationTargetDiscovery` with target discovery in SP12.5 (#1171). This supersedes #1169's
  "the #965 cached semaphore list moves *with signal configuration*" wording: the cache is target
  discovery, so it follows SP12.5, while #1169 closes on the signal-configuration scope.

## Demands on Goal 9B

### D1 — Who owns a lit signal

The ledger knows, for every proceed aspect, the train it was cleared for. A dispatcher sees only
the aspect (`all_signal_aspects`) and, via `hasClearedSignals`, a per-train yes/no. It cannot ask
*"which train is this signal lit for?"*, which is the question behind a stuck opposing movement.

**Goal 9B demand:** a read-only ownership view (semaphore → train) exposed through the facade or
perception, never the ledger itself.

### D2 — Duplicate semaphore caches

The kernel's semaphore cache (`allSemaphores()`, Issue #965 — on the service in SP12.3, in
`ReservationTargetDiscovery` from SP12.5) and `DefaultNetworkPerceptionPort`'s semaphore cache both scan the same grid once and keep the same
list. Kept for now: the kernel must not depend on a port, and the port must not reach into the
kernel. Listed for the SP12 duplicate-check report; see the `allSemaphores` bullet above for the
#1169 wording.
