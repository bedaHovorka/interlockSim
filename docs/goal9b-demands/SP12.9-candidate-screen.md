# SP12.9 — Candidate geometry screening: seams for Goal 9B

> SP12 status index: [SP12-routing-decomposition.md](SP12-routing-decomposition.md) collects the Goal 9B seam list, the duplicate-check report and the size numbers for all SP12 leaves (SP12 is still open, #1159). This page keeps the leaf evidence.

**Issue:** bedaHovorka/interlockSim#1210 (Goal 1B, SP12.9; parent SP12 #1159) · **Date:** 2026-10-25

SP12.9 moved the **read-only candidate geometry screening** — *is this route request, or one of its
candidate paths, geometrically admissible at all?* — out of `DefaultPathReservationService` into a
new class, `RouteCandidateScreen` (same package, `internal`). It is a pure extraction: no behaviour
change, no public API change, no log or denial text change. The reason for the leaf was size: the
service's class body had 916 code lines after SP12.1–SP12.6, over detekt's `LargeClass` limit of 800.

## What moved

| Moved into `RouteCandidateScreen` | Was in the service as |
| --- | --- |
| `allBlocksCache` + `footprintOf` (graph-scan footprint of a train, Issue #893) | private lazy property + private helper |
| `rejectNonOrientedStart` (Step 0 oriented-origin guard, Issue #1188) | private helper |
| `rejectNonContiguousStart` (Step 0 contiguity guard, Issue #893) | private helper |
| `screenRearFacingEnds` (Step 1.5, G8, Issue #1064) | private helper |
| `screenDivergentCandidates` (Step 1.6, Issue #1066) | private helper |
| `rearFacingEndReason` + `arrivalSegmentAt` | private helpers |
| `forwardOnlyPathInfo` (Issue #904 / #938 trimmed PathInfo) | private helper |

Moved first, in their own commit, because three units share them (the screen, the candidate
commit/finalize code that SP12.10 extracts next, and the service's `classifyExhaustedAttempt`):

| Now top-level `internal` | Was in the service as |
| --- | --- |
| `GeometricFailures`, `recordGeometricFailureOnce` (`GeometricFailures.kt`) | private nested data class + private helper |
| `separatorLabel` (`SeparatorLabel.kt`) | private helper |

The two origin guards sit next to each other in the class: the Step 0 END-side twin of the
oriented-origin rule belongs with them. `forwardOnlyPathInfo` stays reachable from the service
(`internal`) because the candidate commit still builds the merge candidate with it.

What stayed on the service: the orchestration — `reservePath` calls each guard and screen in the
same order as before — and everything that mutates (block reservation, switches, signals, merge).
The screen never mutates, which is why a refused request or screened-out candidate leaves nothing
to roll back.

## Seams: what a Goal 9B dispatcher may call, and what stays private

**Call directly:** nothing new. The screening is not a dispatcher input; its verdicts reach a
dispatcher as the existing `ReservationResult` denials (`GeometricallyImpossible`,
`NonContiguousStart`, `DivergesFromHeldRoute`), whose reason strings were not touched.

**Keep private (`internal` in `RouteCandidateScreen`):**

| Function | Why a dispatcher must not call it |
| --- | --- |
| `rejectNonOrientedStart`, `rejectNonContiguousStart` | Request-level guards that only make sense as Step 0 of one `reservePath` call; the contiguity guard reads the live footprint. The dispatcher sees the same verdict as a typed result. |
| `screenRearFacingEnds`, `screenDivergentCandidates` | Operate on the raw candidate enumeration of one request and return indexed survivors that later denial reasons depend on. Probing them directly would be a second opinion about which route to set, which SP5 removed. |
| `forwardOnlyPathInfo` | Builds the trimmed PathInfo of a *candidate that is about to be reserved*; meaningless outside a reservation transaction. |
| `footprintOf` | A graph scan of block occupancy by train name; the observation port already gives a dispatcher the state it may see. |

## Where the Goal 9B demands would land

No demand is addressed here. The extraction only puts the screening rules in one place:

- **A stricter origin policy** (for example a dispatcher-supplied origin that must additionally be
  a boundary of the train's *front* block) is a new guard beside the two `reject*` functions, not a
  change in the service.
- **A structured denial** (a machine-readable reason instead of the English string) would replace
  the `String` returned by `rearFacingEndReason` and the `GeometricFailures.reason` it feeds.

## Notes for the SP12 close-out

Recorded during the #1212 review round, so the close-out's duplicate check can rule on them:

- The forward-block exclusion `filterNot { ... .trainName == trainId }` is stated on both sides of
  the new file boundary — in the service's already-owned branch (`DefaultPathReservationService`,
  over the registry's blocks) and in the screen's Step 1.6 probe (`RouteCandidateScreen`, over
  `extractUniqueBlocks` of the candidate). The two statements must keep selecting the same
  candidates; the close-out should host one shared form (precedent: the file-level
  `extractUniqueBlocks`) instead of a third copy after SP12.10 moves its side.
- `forwardOnlyPathInfo` should be hoisted out of `RouteCandidateScreen` during SP12.10: it is not a
  guard or a screen but a PathInfo-construction rule (its consumers are the Step 1.6 probe and the
  Step 2i commit), and keeping it on the read-only screen would give the mutating commit class a
  screen dependency. Hoisting it as SP12.10's first mechanical commit keeps its pins.
