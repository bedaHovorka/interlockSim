# SP10.1 — LLM dispatcher baseline on Červený Újezd: demands on SP8 and Goal 9B

**Issues:** bedaHovorka/interlockSim#1276 (Goal 1B SP10.1, sub-issue of #1157) · feeds SP8 (#1155)
and the #992 audit · **Date:** 2026-10-31

This is the **before** measurement. It records what the LLM dispatcher does on a 4-InOut station
with the prompts and tools as shipped (vyhybna-shaped), before SP8 changes any prompt or tool text.
SP8's acceptance row "LLM pass rate on Červený Újezd recorded" is the **after**. The measurement is
manual and non-gating: `aiSweep` never runs in `build`, `test`, `integrationTest` or CI.

## What SP10.1 delivered

- **`cervenyUjezdAI`** — the LLM arm on `cerveny_ujezd.xml`, in the `ExampleRegistry` CLI map, the
  GUI map and the LLM-example set (`usesLlmDispatcher`). It shares one helper per mode with
  `shuntingLoopAI` (`llmShuntingLoopExample`, `llmGuiShuntingLoopExample`), so the two LLM examples
  differ only in the network XML: `createLlmPlanner`, `MeasuringPlanAdapter`,
  `declareLlmToolCallingRecorder` and, headless, `ThrottlingSimulationController`.
- **`cervenyUjezdRuleBased`** — the rule-based control arm on the same dispatcher-agent stack, the
  `shuntingLoop` console wiring on `cerveny_ujezd.xml` (shared helper
  `ruleBasedAgentShuntingLoopExample`). It exists because `cervenyUjezd` cannot be the control arm of
  a sweep: it is wired with `wireSynchronousDispatcher` (native parity, SP3), declares no
  `AgentDriverLoop`, and `DispatcherRunSummaries.finishAndPersist` writes a run JSON only when an
  `AgentDriverLoop` exists. Every `aiSweep` run of `cervenyUjezd` would exit 0 with no JSON and be
  recorded as `CRASH`. `cervenyUjezd` itself is unchanged.
- Prompts and tools are **unchanged** (BASELINE frozen, REVISED as shipped). The station literals
  and the leaked capacity are recorded below, not fixed.

## Method

The Goal 10 A4 method (`dispatcher-agent/CLAUDE.md`, "Manual-only dispatcher sweep"): one grid per
arm, both into the same `--out` directory, so one `report.md` compares both arms. Absent runs count
as failures: a killed run is recorded as `TIMEOUT_ABORT`, a run that wrote nothing as `CRASH`.

LLM arm grid (kept out of `docs/`; the control grid is the same with
`"example": ["cervenyUjezdRuleBased"]` and no `model` axis):

```json
{
  "endTimeSeconds": 600,
  "repeat": 10,
  "perRunTimeoutSeconds": 900,
  "axes": {
    "example": ["cervenyUjezdAI"],
    "model": ["qwen2.5:7b-instruct"],
    "temperature": [0.28],
    "tickPeriodMs": [0],
    "historyN": [3],
    "maxActionsPerTick": [3]
  }
}
```

The axes are the A4 reference grid (`docs/GOAL_10_SP2C15_FRONTIER_DIAGNOSTIC_SETUP.md` §2) with one
temperature cell, so each arm has the 10 runs the issue asks for. `inferenceTimeoutSeconds` and
`promptVariant` are omitted and keep the shipped defaults.

## What is measured

- Per arm: runs, trains entered, trains exited, success rate, `correctAt1`, no-op rate, and the
  `TIMEOUT_ABORT` and `CRASH` counts.
- Wall time per run, the model and its tokens per second, and the GPU power limit at the start.
- The capacity value the LLM is shown. Expected: the vyhybna default 2
  (`RuleBasedDispatcher.DEFAULT_MAX_CONCURRENT_TRAINS`, read by the BASELINE prompt and by the
  default `DispatchObservation`), while the topology capacity of Červený Újezd is 4.
- Every station literal in the rendered system prompt and tool descriptions (`vyhybna`,
  `ShuntingLoop`, `"kA"`), for the SP8 inventory and the #992 audit.
- Every stall, with its tool-call sequence.

## Results

Measured 2026-10-31 with a jar from PR #1282 (`qwen2.5:7b-instruct`, 85 tok/s, GPU power limit 95 W).
Other agents' Gradle builds and `gemma4` calls shared the machine and GPU. Full tables, per-run rows,
the literal list and the stall table: the measurement comment on #1276.

| | LLM `cervenyUjezdAI` | Control `cervenyUjezdRuleBased` |
| --- | --- | --- |
| Runs / passing | 10 / 0 | 10 / 10 |
| `NATURAL_COMPLETION` / `TERMINATED_EARLY` | 4 / 6 | 10 / 0 |
| `TIMEOUT_ABORT` / `CRASH` | 0 / 0 | 0 / 0 |
| Trains entered / exited (sums) | 126 / 83 | 190 / 170 |
| Trains that left by the wrong InOut | 39 of 83 | 80 of 180 |
| No-op rate (median) | 0.252 | 0.000 |
| `correctAt1` | not computed (null) in every run | not computed |
| Rule-fallback ticks | 154 of 585 | 0 |

**Capacity shown to the LLM: 2** (system prompt admission step, `N / 2` in every cycle header),
while the loop's topology capacity is 4. Both arms ran at most 2 trains at a time.

**Station literals in the rendered prompt and tools:** `ShuntingLoop` once (the `approve_train`
description), `"kA"` three times (the STATION TOPOLOGY header and both `request_route` endpoint
parameters), `vyhybna` never.

**Stalls:** all six early ends have one cause. A train that has not entered yet holds a route
reserved from the wrong InOut (the other InOut on its side, or the far side). When it is approved,
its `InOutWorker` path setup is rejected as non-contiguous, the worker throws a FATAL
`SimulationException`, and the kDisco queue drains.

## Demands on SP8 (#1155)

- **S1 — Entry and exit per train.** The cycle message names no entry InOut for a queued train, the
  queued-origin check in `RequestRouteTool` accepts any InOut except the destination, and the NEXT
  SECTION hint can name an InOut that is not the train's exit (29 of 51 InOut-target hints in traced
  runs). All three assume two InOuts. They cause the six stalls and most wrong exits.
- **S2 — Capacity from the topology** in the prompt, the cycle header and the fallback dispatcher
  (SP3 D5). The synchronous reference run at capacity 4 had 142 failed reservations, so the cap
  cannot be raised without throat-conflict handling (SP3 D1, D4).
- **S3 — Topology text built for the station.** `Switches: none` for 12 unnamed switches, blocks
  rendered as `"unknown"`, signal names that also appear as Block IDs, and a worked EXAMPLE that
  uses `e30` as an endpoint and then forbids it. The EXAMPLE takes the first two InOuts and the
  first signal alphabetically; on this station that is a same-side pair and a signal facing away.
- **S4 — No vyhybna literals** in tool texts: `ShuntingLoop` and `"kA"`.

## Demands on Goal 9B

- **G1 — A dispatcher error must not kill the railway.** A non-contiguous path setup in
  `InOutWorker` is a FATAL exception that ends the run; it should be a refused route the train
  waits out.
- **G2 — Exit choice is a railway fact, not a dispatcher guess.** The rule-based control arm also
  ends 8 of its 18 train journeys per run at the wrong InOut, so target selection on a station with two
  InOuts per side needs a topology answer (SP5 `CandidateTarget`), not a prompt fix.
- **G3 — The measurement pipeline must see FATALs of failed runs.** The sweep report says no run
  logged a FATAL `SimulationException`, while all six stalled logs contain one: the scan result is
  written into the run JSON only for runs that exit 0.
